# 연구 프로토콜 v0.2: VLM 보조 HIL-SERL 보상 라벨의 사람 검토 예산

상태: **v0.2, 사용자 승인 (2026-10-20).** 승인 내용은 `docs/PROTOCOL_결정_초안.md`, 함께 바뀐 것은 `DECISIONS.md` D-28~D-33에 있습니다.
아직 정해지지 않은 것:
- 게임패드 실물 확인 (D-28)
- 실제 물체와 용기 (`LABEL_DEFINITION.md`)
- 온라인 스텝 예산 (P3에서 정함)
- 시드 3개를 5개로 늘릴지 (P3 뒤에 정함, D-31)

이 문서를 바꾸면 새 버전(v0.3)으로 기록합니다. 각 선택의 이유는 `DECISIONS.md`에 있습니다. 용어는 `docs/용어집.md`를 참고하세요.

## 1. 연구 질문

**주 질문 (기본 실험).** SO-101 pick-and-place에서 보상 분류기 라벨을 세 가지 방식으로 만들어 비교합니다.
**A** 사람이 100% 검토, **B** 사람이 25% 검토(시드로 고정한 무작위 에피소드), **C** VLM만 사용.
1. 각 조건에서 사람 검토 시간이 얼마나 드는가? (실측)
2. B(그리고 C)로 학습한 HIL-SERL의 실제 로봇 성공률이 A보다 마진 **δ = 0.20(20%p)** 이상 나쁘지 않은가? (**비열등성**)
   - 판단 방법은 시드별 성공률의 Welch t 구간입니다(D-30).
   - 시드가 적어서 "판단 불가"로 나올 가능성이 큽니다. 그래서 결론의 무게는 사람 시간(실측)과 audit 오프라인 지표에 더 둡니다(D-31).

**부 질문.** 다음을 함께 봅니다.
- 학습 라벨의 정확도·FPR·FNR (100% 검토 대비)
- 블라인드 audit 세트에서 분류기의 정확도·FPR·FNR
- 오프라인 가짜 성공 종료(termination replay)와 온라인 가짜 성공 종료
- 사람 개입 횟수와 시간, 학습 시간과 전체 소요 시간, 실행 실패율, 시드 간 분산

**후속 질문 (기본 실험이 성공한 뒤에만).** 같은 25% 예산에서 무작위, VLM 확신 낮은 것 우선, 가짜 성공 의심 우선 세 정책을 비교합니다.
먼저 오프라인으로 비교합니다(D-07 덕분에 비용이 적음). 예산은 **에피소드 수**와 **사람 시간**(`budget_unit: seconds`) 두 기준으로 모두 비교합니다(D-25). 실제 로봇 비교는 가장 유망한 정책과 무작위 정책 두 개로 제한합니다.

기대하는 답을 미리 가정하지 않습니다. 라벨 정확도가 높아도 로봇 성공률이 높아지지 않을 수 있으며, 리포트는 어느 결과든 보여 줄 수 있어야 합니다.

## 2. 단위와 정확한 정의

| 용어 | 정의 |
|---|---|
| 에피소드 | LeRobot으로 녹화한 시도 하나 (`gym_manipulator`, `mode: record`, `terminate_on_success: false`) |
| 키프레임 (라벨 단위) | 프레임 번호 0, s, 2s, ... 와 마지막 프레임. 10fps에서 s = 5 (0.5초 간격) |
| 사용 가능한 에피소드 | 다시 녹화하거나 중단하지 않았고, 모든 카메라 영상이 열리고, 길이가 2초 이상인 것. 제외 사유는 기록합니다. |
| 풀 (pool) | train과 val로 나뉜 사용 가능한 에피소드 |
| audit 세트 | audit으로 나뉜 사용 가능한 에피소드. 블라인드로 라벨링하며, 어떤 결정에도 쓰지 않습니다. |
| 검토 단위 | 에피소드 하나 전체(그 안의 모든 키프레임). `hilreview review` 도구로 검토합니다. |
| 예산 | k = round_half_up(비율 × 풀 에피소드 수). 예: 88개의 25%는 22개 |
| 조건별 라벨 | 고른 k개 에피소드는 사람 라벨, 나머지는 VLM 라벨. 애매함·무효·라벨 없음은 학습에서 빼고 개수를 셉니다. |

라벨의 뜻은 `docs/LABEL_DEFINITION.md`를 보세요.

## 3. 데이터 수집 (사용자가 실행, LeRobot HIL-SERL 가이드처럼 텔레오퍼레이션)

- **장치**: 녹화는 게임패드로 합니다(D-28). 물체와 용기는 `LABEL_DEFINITION.md`에 적습니다.
- **세션**(서로 다른 시간이나 날)은 **4개**이고, 세션마다 약 30개를 녹화합니다. 에피소드마다 `session_id`를 기록합니다.
- 모든 세션에서 **수집 방식**을 섞고, 에피소드마다 의도한 방식을 기록합니다(D-32).
  - `success_attempt` (약 50%): 정상적으로 성공 시도
  - `near_miss` (약 30%): 물체를 용기 위나 옆까지 가져갔다가 바깥에 떨어뜨림 (가짜 성공을 유도하는 장면)
  - `clear_failure` (약 20%): 확실한 실패
- 성공한 뒤에는 물체를 놓고 **약 2초 그대로** 둡니다(D-32).
- 목표 크기: 사용 가능한 에피소드 **약 120개** → audit 약 30개, val 약 18개, train 약 72개.
- LeRobot이 녹화 중 성공 버튼(게임패드 Y, 키보드 `s`)으로 기록하는 성공 보상은 함께 저장되지만, **어떤 조건에서도 라벨로 쓰지 않습니다**. 나중에 추가 기준으로 분석할 수는 있습니다.
- 강화학습의 시연 데이터 보상에도 이 값을 쓰지 않고, 조건마다 그 조건의 분류기로 다시 매깁니다(D-29).
- 수집 기록(종이나 CSV)을 남기세요: 에피소드 번호 → session_id, collection_mode, 메모, 제외 사유.

## 4. 작업 순서 (사전 등록)

1. `LABEL_DEFINITION.md`와 VLM 질문문(`labeling/vlm.py`의 `PROMPT_VERSION`)을 고정합니다. 질문문 다듬기는 **예비 실험 데이터로만** 합니다(8절). 실험 에피소드로는 절대 하지 않습니다.
2. 데이터를 수집합니다(3절). 키프레임을 내보냅니다: `hilreview export-keyframes` (노트북).
3. 데이터 나누기를 고정합니다: `hilreview split --episodes episodes.jsonl --out splits.json`. 한 번 만들면 덮어쓰기를 거부합니다.
4. **블라인드 audit 라벨링을 먼저 합니다**: `hilreview review --purpose audit`. 하루 이상 지난 뒤, 30% 일부를 다시 블라인드로 라벨링합니다(`--purpose audit_repeat`).
5. 풀과 audit의 모든 키프레임을 VLM으로 라벨링합니다: `hilreview vlm-label` (로컬 서버). `--limit`으로 먼저 소량 시험해 봅니다.
6. 풀 전체를 무작위 순서로 **한 번만** VLM 제안을 보면서 검토합니다: `hilreview review --purpose pool_review --vlm ...`.
7. `hilreview run --config <파일 설정> --export-labels`를 실행합니다. 조건·반복 실행별 라벨 파일과 사람 시간·라벨 품질 결과가 나옵니다. 프로토콜을 어긴 검토 파일은 거부합니다(예: audit 에피소드를 VLM 제안을 보면서 검토한 경우).
8. 조건과 학습 시드마다 `hilreview build-reward-dataset` → `lerobot-train`(보상 분류기)을 실행합니다. 분류기 설정, 스텝 수, 시드는 **모든 조건에서 같게** 합니다.
9. val과 audit 키프레임에 `hilreview score`를 실행하고, `classifier_scores`를 넣어 7번을 다시 실행합니다. 그러면 audit 지표, termination replay, 짝지은 비교가 나옵니다.
   - 9-1. 조건마다 시연 데이터(train의 `success_attempt` 에피소드 전부)의 보상을 그 조건의 분류기로 다시 매깁니다(D-29, 규칙 수정 D-35): `hilreview score-frames` → `hilreview relabel-demos`. `--threshold`/`--success-reward`는 온라인 설정과 같은 값.
10. 블라인드 순서표대로 온라인 HIL-SERL을 실행합니다(6절). 이때 다른 무거운 작업은 돌리지 않습니다(D-33).
11. 블라인드를 풀고 요약합니다: `hilreview online-summary`.

이 순서와 달라진 점은 날짜와 이유를 적어 `results/real/DEVIATIONS.md`에 기록합니다.

## 6. 온라인(실제 로봇) 평가

- **조건 맞추기**: 다음을 모두 같게 합니다.
  - 시연 에피소드 목록, HIL-SERL 설정(`TrainRLServerPipelineConfig`), `success_threshold`
  - 온라인 스텝 예산 (P3에서 잰 뒤 정함)
  - 하드웨어, 작업 공간, LeRobot 커밋 `8c920c42` (D-33)
  - 다른 무거운 작업을 돌리지 않음 (D-33)

  다른 것은 분류기와, 그 분류기로 다시 매긴 시연 데이터 보상뿐입니다(D-29).
- **블라인드와 순서**: `hilreview schedule --conditions A,B,C --replicates R --seed <S>`로 순서표를 만듭니다. 작업자는 실행 ID만 봅니다. 조건이 적힌 key 파일은 모든 실행과 성공 판단이 끝날 때까지 열지 않습니다.
- **개입**: LeRobot 안내에 따라 같은 사람이 게임패드로 개입하고(D-28), 그 사람도 조건을 모릅니다.
- **평가 에피소드**: 각 실행 후, 정해 둔 물체 시작 위치 **10곳 × 2회 = 20개**를 무작위 순서로 돌립니다. 개입은 하지 않습니다. 성공 판단은 사람이 `LABEL_DEFINITION.md` 기준으로 합니다. 보상 분류기는 성공을 **절대** 판단하지 않습니다.
- **기록**: `hilreview log-episodes`로 에피소드가 끝날 때마다 글자 2개를 입력합니다(D-26). 에피소드마다 `OnlineEpisodeRecord` 하나(run_id, 단계, 종료 이유, 사람 판단, actor 기록의 개입 스텝/전체 스텝/fps), 실행마다 `RunRecord` 하나(상태, 소요 시간)를 남깁니다. 개입/전체 스텝은 실행이 끝난 뒤 `hilreview extract-interventions`로 learner의 오프라인 wandb 기록에서 채웁니다(D-36, HIL-SERL 설정에 `wandb.enable=true`, `wandb.mode=offline` 필수).
- **안전**: 모든 실행은 사용자가 시작하고 멈춥니다. 비상 정지 버튼에 손이 닿아야 하고, 끝단(EE) 이동 범위가 설정되어 있어야 합니다(`lerobot-find-joint-limits`). 이 저장소의 어떤 코드도 로봇을 움직이지 않습니다.

## 7. 통계 분석 계획

- 기본 보고: 추정값과 95% 구간. 비율은 Wilson, 키프레임 지표는 에피소드 단위 부트스트랩, 조건 간 차이는 같은 audit 세트에서 **에피소드 짝 부트스트랩**을 씁니다.
- 합친 값 옆에 시드별 값과 시드 간 표준편차를 항상 같이 보여 줍니다.
- 비열등성(주 질문 2)은 시드별 성공률로 계산한 "X − A"(X = B, C)의 Welch t 단측 95% 구간으로 판단합니다(D-30).
  - 아래쪽 끝 > −δ이면 "비열등", 위쪽 끝 < −δ이면 "열등", 그 밖은 "판단 불가"입니다.
  - 에피소드를 모두 합친 Wilson 구간은 설명용입니다.
  - 계획용 추정으로는 시드 3개일 때 결론이 **판단 불가**로 나올 가능성이 큽니다(`docs/RESOURCE_ESTIMATES.md` 1-1절). 그 경우 "차이 없음"이 아니라 "판단 불가"라고 보고합니다.
- 시드는 조건당 최소 3개입니다. 5개로 늘릴지는 P3에서 잰 시간만 보고, 본 실험 결과를 보기 전에 정합니다(D-31).
- 시드 몇 개로 통계적 유의성을 주장하지 않습니다. audit이나 온라인 결과를 본 뒤에 임계값, 지표, 조건 정의를 바꾸지 않습니다. 탐색적 분석은 탐색적이라고 표시합니다.
- 부정적 결과와 차이 없음 결과도 보고합니다. 이미 하나 있습니다: 가짜 성공 우선 정책 1판 (`DECISIONS.md` D-17).
